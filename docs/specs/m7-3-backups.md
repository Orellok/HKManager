# M7.3 – Weekly backups and restore procedure

Source: SPEC.md 8 (backup, retention, no encryption, accepted risk), 0, 13 VERIFY-05; docs/verify/VERIFY-05-drive-upload.md; docs/PROGRESS.md lead decisions 2026-11-23 (VERIFY-05) and the M7.2 carry list. Criteria set by the lead under the owner's pre-approval.

## Acceptance criteria

### Backup job
1. `.github/workflows/backup.yml` runs weekly (Saturday 02:41 UTC) for production and on `workflow_dispatch` with an `environment` input (production default, staging optional – staging holds no real data and is for trying the pipeline). `permissions: contents: read`, one run at a time, a timeout. Missing secrets fail the job and are named (`SUPABASE_ACCESS_TOKEN`, the environment's DB password, `GOOGLE_DRIVE_BACKUP_CLIENT_ID`, `GOOGLE_DRIVE_BACKUP_CLIENT_SECRET`, `GOOGLE_DRIVE_BACKUP_REFRESH_TOKEN`). No new GitHub secret beyond the three Google ones.
2. Each run produces one archive `hkmanager-<environment>-<YYYY-MM-DD>T<HHMMSS>Z.tar.gz` holding `db/data.sql` (data of `public` and `auth`, pg_dump COPY format, via the pinned Supabase CLI `supabase db dump`), `db/schema.sql` (reference), every object of every Storage bucket under `storage/<bucket>/<path>` (Storage API, service key read at run time with the existing access token and masked), and `manifest.json` (format version, environment, time, commit, latest migration, bytes + SHA-256 per file and object, row count per table, object content types).
3. Upload to Google Drive with the owner's refresh token (separate OAuth client, scope `drive.file` only): the job uses a folder "HKManager backups" created by the app itself (found again by name among the app's files, created when missing), uploads with a resumable session, and verifies the upload by reading back the Drive file's size and MD5 and comparing them with the local file. The job never creates sharing permissions or links.
4. Retention (SPEC 8): only after the new upload is verified, the job keeps the 12 newest backups of the same environment (ordered by the time in the file name) and permanently deletes older ones. Only files in that folder whose names match the environment's backup pattern are candidates. No verification → nothing is deleted.
5. Any failure (dump, Storage, Google, verification, retention) exits non-zero so the run fails and GitHub emails the admin. A revoked or expired refresh token (`invalid_grant`) fails with a message telling to re-run the token script.
6. Public repository: the log shows only step outcomes, counts, sizes and the archive name. CLI output is discarded; Google and Storage errors are reported by HTTP status and error code only (never response bodies, object paths, personal data or tokens). No artifacts or caches with data. Work files live under `$RUNNER_TEMP` (mode 0700), never in the repository workspace, and are deleted by the script and again by an `always()` step.
7. Encryption: none, per SPEC 8 (owner decision): protection relies on the Google account; recorded in the owner docs.

### Owner token script and docs
8. `scripts/backup/get-drive-token.mts` (Node built-ins only) takes the downloaded Desktop OAuth client JSON, runs a loopback consent (127.0.0.1, random port, PKCE S256, state check, `access_type=offline`, `prompt=consent`, scope `drive.file` only, 5-minute timeout), requires a refresh token and the `drive.file` grant, writes client id, client secret and refresh token to the git-ignored `.env.drive-backup.local` with mode 0600 (also when replacing it with `--force`), proves the token by finding or creating the backup folder, never prints the token, and prints the next steps.
9. `docs/setup/backups.md` (Hebrew): OAuth client in a published ("In production") project, Drive API, running the script (Node >= 22.18), setting the three secrets, first manual run, checking Drive, the 60-day schedule rule, token revocation/renewal, what a failure email means.

### Restore
10. `scripts/backup/restore.mts` restores an archive into a project whose schema came from the repository migrations at the manifest's commit: verifies every checksum; loads `db/data.sql` in one transaction after emptying the dumped tables, refusing a target that already holds data beyond the migrations' seed unless `--replace` is given; compares row counts with the manifest; uploads every Storage object (upsert) and checks each SHA-256. Secrets come from environment variables, never arguments. `docs/setup/restore.md` (Hebrew) is the written procedure, including the steps after a restore (VAPID secrets, push function, Netlify variables, OAuth redirect URLs).
11. `scripts/backup/restore-drill.mts` proves the procedure on the local stack: backup → `supabase db reset --no-seed` (a fresh project) → restore → every dumped table has the same row count and content hash, every object downloads with the same SHA-256. It is run once and its result recorded in `docs/setup/restore.md`; a staging drill by the owner before production go-live is part of the runbook.

### Carry-overs (M7.2)
12. (a) `generate-push-keys.mts` sets mode 0600 after writing, also on `--force`; (b) after the install button opens Chrome's dialog, focus moves to the install heading; (c) pg_net: revoke the `net` grants from `anon` / `authenticated` where the migration role can; otherwise prove by test that neither role can reach `net` through the Data API and record why; (d) `configure_push_reminders` accepts only `https://<20-letter project ref>.supabase.co/functions/v1/push` (plus the local hosts); (e) docs state Node >= 22.18 for the scripts.

### General
13. No new dependency. Tests named M7.3-n: unit (Drive client against a fake Google, retention, manifest/row counts, safe errors, token-script flow, restore checks, key-file mode), integration (Storage export against the local stack, pg_net reachability, function URL rule), E2E (install focus).
